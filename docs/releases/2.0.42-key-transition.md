# Hardened NanoKVM 2.0.42 Manual Key Transition

> TRANSITION_RELEASE_BLOCKED_PENDING_RAW10_PHYSICAL_GATE_AND_OFFHOST_BACKUP
>
> Publication is prohibited until the exact app `2.0.40`/raw.10 physical
> transition passes and one encrypted production-key backup is moved off-host.

This is an application-only manual transition release. It does not update the
base system and does not change the application preview, system preview or
stable online channels.

## Why this release exists

The legacy metadata-signing private key is unavailable. Existing devices
therefore cannot receive a production-key bridge through the old signed online
channel. App `2.0.42` is installed manually through the authenticated Offline
Update page and adds the new production public key without removing historical
trust during the migration window.

## Required manual installation

1. Download `hardened-nanokvm-kvmapp-2.0.42.tar.gz` and its checksum from this
   exact GitHub release.
2. Require SHA-256
   `aa0cd78c1b2e9951f216826c44b4b7ff2fb211fc1980540366f8f5b1f7e0dd20`.
3. Sign in to NanoKVM and open **Settings → Update → Offline Update**.
4. Upload the complete archive. Do not unpack or modify it.
5. Wait for the backend restart, sign in again, and confirm app `2.0.42`.

Do not install raw.12 before this bridge. After the combined RC12 release is
published, bridged devices may enable the system Preview channel and install
raw.12. A new full RC12 SD image already contains app `2.0.42` and does not
need this separate step.

## Security changes

- Retains the historical public key and IDs `hardened-system-dev` and
  `hardened-system-test` during the migration window.
- Adds production key ID `hardened-system-prod-2026q3`.
- Installs an explicit three-ID allowlist policy.
- Atomically installs the bundled public trust set on the first start of the
  new Rust server, even when the restart began under an older init script.
- Rejects unsafe key names, symlinked/untrusted source paths, malformed policy
  and policy-excluded key IDs.

Legacy IDs are not removed in this release. Their later retirement requires a
separate application release after the migration window.

## Tested migration paths

- App `2.0.41` / raw.11 on the primary test device: immediate trust,
  historical and production signatures, reboot persistence, SSH identity,
  account and runtime passed.
- App `2.0.40` compatibility on raw.12: the same checks passed. The exact
  app `2.0.40` / raw.10 physical gate remains a publication blocker and is not
  inferred from the raw.12 result.

## Recovery alternatives

- If web access works, use the manual Offline Update procedure above.
- Managed devices may install the same complete archive through the
  authenticated offline-upload API or SSH administration.
- Devices without working web or SSH access require a full RC12 SD reflash.
- Enabling unsigned online updates is not an approved migration method.
